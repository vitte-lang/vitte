Types composés et qualifiés

[4]i64          // tableau fixe de quatre entiers
&Point          // référence
&mut Point      // référence mutable
*u8             // pointeur
module::Point   // type qualifié

La grammaire décrit les références avec &T ou ref T, éventuellement suivies de mut ; les pointeurs avec *T ; les tableaux avec [expression]T ; et les chemins de type avec des paramètres génériques entre chevrons ou crochets.

Génériques et alias

type Option<T> = ?T;

form Paire<T> {
    premier: T,
    second: T,
}

proc identite<T>(valeur: T) -> T {
    return valeur;
}

Le sous-ensemble exécuté des formes génériques accepte des paramètres de types simples ou composés. Les spécialisations scalaires à un paramètre ont été validées avec i64, bool, u64, f64, string et char. Les deux compilateurs exécutent Pair<i64, bool>, Triple<i64, bool, u64> avec son champ Box<U>, et une forme à 40 paramètres qui vérifie les substitutions aux positions 33 et 39. Les tests rejettent les mauvais types de champs, les listes d’arguments trop courtes ou trop longues et un champ composé incompatible. La pile des substitutions et la table des spécialisations s’agrandissent selon les besoins. Les deux compilateurs génèrent puis exécutent une unité avec 513 spécialisations concrètes distinctes ; ce test ne fixe pas une limite théorique de capacité. Les compositions à un paramètre comprennent Wrapper<T>, Outer<T>, une référence récursive derrière un pointeur et l’application Emballage<Boite<i64>>. La suite frontend native exécute aussi des procédures locales à paramètres directs scalaires, ainsi qu’une procédure select_box<T, U> dont les paramètres et le retour sont respectivement Box<T>, Box<U> et Box<T> ; une fixture négative vérifie le rejet de deux arguments Box incompatibles pour un même T. Ces tests n’établissent toujours pas le support bootstrap, les appels importés ou qualifiés, la spécialisation imbriquée depuis une procédure générique, les bornes ni where. Consultez formes-generiques.vit, compositions-generiques.vit et native_bootstrap_parity_test.py. Les champs mal typés sont rejetés ; un type concret inconnu reçoit E0510.

Nullable : écart à résoudre entre les sources

Les sources de modules/core emploient le type nullable ?T et représentent l’absence avec null. Toutefois, la production type de grammar/vitte.ebnf ne liste pas explicitement cette forme. Aucun des tests d’exécution audités ne prouve son acceptation et sa génération C17 ; l’exemple suivant illustre le code source de core, pas une forme garantie par l’EBNF ou le backend natif.

proc valeur_ou_zero(valeur: ?i64) -> i64 {
    if valeur != null {
        return valeur;
    }
    return 0;
}

Conversions

Le mot de conversion as est accepté et compilé dans les tests natifs, notamment pour convertir des valeurs en u8 et f64. Il n’apparaît pas dans la production d’expression de l’EBNF actuelle. Une conversion explicite annonce le changement de type ; elle ne prouve pas à elle seule que la valeur reste dans la plage de destination. La bibliothèque core::convert fournit des conversions vérifiées pour certains couples de types.

Règle de consultation

Utilise le type le plus étroit qui exprime réellement ton domaine, puis vérifie la disponibilité et les règles de conversion sur la cible de compilation utilisée.
