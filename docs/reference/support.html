Le dépôt possède plusieurs chemins de compilation

Le CLI envoie un sous-ensemble vers le frontend natif (HIR, IR, C17) et conserve un chemin bootstrap/compatibilité pour d’autres formes. « Compilé » signifie ici qu’un test du dépôt produit un exécutable et le lance ; une sortie C seule ne prouve pas l’exécution. Les résultats ci-dessous décrivent le commit audité, pas une garantie pour toutes les cibles.

Comment lire la matrice

  • EBNF : la construction est écrite dans grammar/vitte.ebnf. « Non » signale une extension utilisée ailleurs dans le dépôt.
  • Analyseur : le niveau nomme le parseur ou la commande couverte par une fixture. check inclut le parsing, puis continue vers la sémantique.
  • Compilation : HIR/IR + C17 + exécution est une preuve du backend natif ; compatibilité + exécution passe par le chemin bootstrap. « Non prouvé » veut dire qu’aucun test ciblé consulté n’établit ce niveau.
  • Disponible : l’étape indiquée dans la ligne est vérifiée pour la forme citée ; un parsing réussi seul ne prouve pas la compilation. Expérimental : la forme est partielle ou son parcours complet n’est pas encore confirmé. Non implémenté : un rejet explicite ou une absence d’implémentation est documenté pour le cas et le chemin de compilation indiqués.

Ces statuts décrivent la preuve disponible pour Vitte {{ site.vitte_version }} et le cas nommé. « Expérimental » est un statut documentaire de couverture, pas une garantie de stabilité ni une annonce de feuille de route.

Commandes et preuves exécutées

Les commandes suivantes ont été lancées sur le dépôt local le 27 octobre 2026 :

  • make test-grammar test-sema test-native-frontend-subset test-native-bootstrap-parity test-runtime : synchronisation EBNF/tokens réussie, 5 fixtures de grammaire, cas sémantiques réussis, 9 cas natifs valides et 18 invalides, 7 cas de parité parseur/AST, 4 cas de parité sémantique et 11 programmes runtime réussis.
  • Le test natif vérifie explicitement les sorties IR et C17 pour tableaux, formes et variantes pick avec charge utile. Il vérifie aussi le rejet backend d’une forme générique et d’une boucle for sur tableau.

La vérification check-ebnf-frontend-sync porte sur les mots-clés, les opérateurs et la couverture des tokens ; elle ne prouve pas que chaque production EBNF est supportée par chaque backend.

Que faire lorsqu’une construction échoue ?

Réduisez le fichier, identifiez la première étape qui refuse le programme, puis comparez son résultat à la ligne correspondante de cette matrice. Le guide d’installation et de dépannage détaille les commandes lex, parse, check, compile et run, ainsi que les vérifications de chemins de modules et de compilation C.
