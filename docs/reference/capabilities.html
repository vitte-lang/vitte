Portée des preuves

Cette matrice décrit le code et les tests présents dans le dépôt, pas une promesse de compatibilité complète. Le compilateur 0.1.1 n’est pas prêt à être publié : ses gates de release restent ouverts. Le CLI n’expose pas d’identifiant de build ; une version 0.1.1 détectée ne suffit donc pas à certifier un binaire local. Le fichier JSON versionné est la source utilisée par la commande VS Code Vitte: Show Capabilities ; il contient les preuves par ligne et les références de suivi.

Statuts

  • Implémenté : comportement présent et test automatisé pour le périmètre indiqué.
  • Partiel / expérimental : comportement limité ou dépendant du contexte ; la limitation est précisée.
  • Planifié : non annoncé comme capacité active ; le travail est enregistré ci-dessous.
  • Indisponible : le toolchain 0.1.1 n’exécute pas ce comportement.

Un fournisseur LSP n’est annoncé à VS Code que si la ligne correspondante est annoncée dans le manifeste et possède une preuve automatisée. Les réponses de complétion viennent du serveur de langage : l’extension ne remplace plus un délai ou un échec par des candidats heuristiques ou mis en cache.

Installation, activation et toolchain

L’extension démarre ses services à l’ouverture d’un fichier .vit, .vitl ou .vitte, ou d’un workspace contenant vitte.toml, .vitte/config ou un fichier de configuration éditeur. En Restricted Mode, le LSP, les compilateurs et les outils du projet restent suspendus jusqu’à l’approbation du workspace.

Le VSIX contient le client, le serveur LSP, ses dépendances runtime, la grammaire, les snippets, les schémas et l’icône. Il ne contient pas le compilateur. Une installation locale depuis un VSIX n’exige ni checkout du dépôt ni réseau ; les actions de compilation ont besoin d’un compilateur local 0.1.1 vérifié. La version de l’extension est 2.3.9 ; le serveur LSP intégré reste compatible avec la série 2.3.x.

La commande Vitte: Detect Project indique le dossier actif, la racine retenue, le fichier de configuration CLI et la règle appliquée. Sans vitte.project.root, elle choisit le plus proche de vitte.toml ou .vitte/config en remontant depuis le fichier actif ; à défaut, elle prend le dossier de workspace correspondant. Les réglages, toolchains et racines de modules sont lus séparément pour chaque dossier d’un workspace multi-root. vitte.config.json et .vitte/config.json peuvent activer l’éditeur et fournir le schéma JSON, mais le CLI 0.1.1 ne les charge pas comme configuration de compilation.

Pour le compilateur, la résolution suit, dans le dossier courant, vitte.compiler.path, vitte.toolchain.root/bin, les binaires du projet, les variables VITTE_BIN_DIR/VITTE_TOOLCHAIN_ROOT/VITTE_ROOT/VITTE_HOME, puis les installations utilisateur et PATH. vitte.serverPath sélectionne un module JavaScript personnalisé, vitte.lsp.path un exécutable externe ; le serveur empaqueté est le défaut. Les imports recherchent le fichier courant, la racine de son dossier/projet, vitte.modulePaths (transmis au CLI dans VITTE_MODULE_PATH), puis les dossiers modules de l’installation utilisateur/toolchain. Les réglages se consultent dans l’Output channel Vitte Language Server ; la commande Vitte: Restart Language Server est disponible après un changement de configuration.

La barre d’état ouvre Vitte: Status and Project Health. Les commandes Vitte: Project Actions, Vitte: Select Compiler et Vitte: Select Build Target sont également accessibles depuis la palette. L’extension n’ajoute pas de raccourcis clavier par défaut. Les notifications de commandes au démarrage sont désactivées par défaut et peuvent être activées avec vitte.notifications.showStartupCommands. La traduction anglaise/française des parcours couverts se choisit avec vitte.lang ; voir CAP-UX-001 pour les chaînes et vérifications d’accessibilité restantes.

Exclusions et suivi

  • CAP-EXT-001 — Tester le minimum VS Code 1.105 et conserver une preuve de contenu VSIX hors réseau : serveur, dépendances runtime, grammaire, snippets et icône.
  • CAP-EXT-002 — Implémenter des providers réels pour les rapports dead-code, couverture de documentation et API, ou garder ces actions explicitement indisponibles.
  • CAP-LSP-001 — Remplacer les index source par les API de symboles/types du compilateur, puis tester les overloads, l’inférence d’éditeur, les relations d’appels/types et les cibles générées. Les providers annoncés ici restent limités à leurs cas source prouvés.
  • CAP-LSP-002 — Exposer au compilateur les scopes, types, visibilités, overloads et signatures avant d’élargir la complétion source ; décider si les appels de procédures nommés entrent dans la grammaire.
  • CAP-CLI-001 — Implémenter ou retirer explicitement vitte test et vitte fmt du contrat du pilote natif ; maintenir test et formatage indisponibles jusqu’aux tests de parité.
  • CAP-PROJECT-001 — Exposer au LSP une requête compilateur canonique pour les racines source, paquets et fichiers Vitte générés. D’ici là, déclarer les racines supplémentaires dans vitte.modulePaths ; aucune relation de module généré n’est devinée depuis un manifest.
  • CAP-LSP-003 — Exposer l’usage, la visibilité et les destinations d’import uniques depuis le compilateur avant d’ajouter organiser/supprimer/importer/qualifier au-delà des suggestions machine-applicables exactes.
  • CAP-PLATFORM-001 — Fermer les gates Linux x86_64, macOS arm64 et Windows x86_64, puis établir un toolchain cross avant toute annonce multi-cible.
  • CAP-SUGGEST-001 — Garder les moteurs inline opt-in jusqu’à validation de leurs sorties via le compilateur/LSP et rejet des résultats périmés.
  • CAP-DBG-001 — Faire exécuter par la CI les scénarios DAP de la révision courante avec la version précise du compilateur ; corriger macOS et ajouter Windows avant d’élargir le support ou d’activer le backend par défaut.
  • CAP-DBG-002 — Exposer des mappings source canoniques et des emplacements d’erreur runtime structurés à DAP pour le code généré et les programmes multi-modules. D’ici là, seuls les emplacements DWARF/ #line et les signaux natifs sont mappés.
  • CAP-LSP-004 — Ajouter des tests automatisés de rejet des réponses obsolètes et de cancellation après édition, changement de settings, watcher, workspace et toolchain ; couvrir les limites, caches, symlinks, URI encodées, chemins non ASCII et règles de casse Windows/macOS.
  • CAP-UX-001 — Localiser les titres de commandes, réglages et messages historiques ; ajouter des régressions d’accès clavier, lecteur d’écran, contraste élevé et mouvement réduit avant d’annoncer toute la couverture UI.

Le VSIX embarque le client et le serveur LSP, ses dépendances de production, la grammaire, les snippets et l’icône. Il ne contient pas le compilateur Vitte : les commandes de compilation nécessitent un toolchain local compatible. Une fois le VSIX installé, les fonctionnalités incluses ne font pas de téléchargement réseau.

Références détaillées : support du langage par construction, CLI et diagnostics, et matrice JSON versionnée 1.0.13.
