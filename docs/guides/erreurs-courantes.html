Les codes et chemins ci-dessous ont été reproduits avec Vitte 0.1.1.

Vérification locale effectuée le 28 octobre 2026 sur les fixtures liées. Un diagnostic décrit le premier défaut rencontré sur ce cas ; après sa correction, une autre étape peut révéler une erreur suivante. Consultez toujours la sortie de votre propre version.

Anatomie d’un diagnostic

Un diagnostic terminal peut comporter le code public, un titre, la phase, un détail de type ou d’import, une plage source, une explication, une aide et parfois une correction automatique suggérée. Par exemple, une erreur de syntaxe ressemblant à error[E0201]: expected token indique que le parser attendait un token requis à cet endroit.

  • Le code est la référence stable à rechercher et à joindre dans un signalement, par exemple E0401.
  • La phase distingue lexer, parser, import, résolution de nom, vérification de type, backend ou autre étape.
  • La plage pointe le token ou l’expression concernés. L’erreur peut se trouver juste avant ou après le soulignement si un délimiteur manque.
  • Le détail donne le symbole, le type attendu/reçu, le module recherché ou l’étape du backend.
  • L’aide propose une direction de correction. Une suggestion marquée applicable automatiquement ne dispense pas de relire le changement.

Pour obtenir l’explication enregistrée pour un code, lancez :

build/bin/vitte explain E0512

Pour une sortie destinée à un outil, demandez le format JSON :

build/bin/vitte check examples/diagnostics/invalid_not_operand.vit \
  --quiet --no-color --diagnostic=json

Les formats terminal, JSON, SARIF et LSP exposent des représentations différentes du même problème. Gardez le code symbolique et le code public quand vous rapportez une anomalie.

Dépanner dans l’ordre du pipeline

  1. Identifiez le binaire et le répertoire. Lancez build/bin/vitte --version, vérifiez pwd et confirmez le chemin du fichier.
  2. Examinez la lecture des caractères. Une chaîne ou un commentaire inachevé est un problème lexical ; une faute de token n’est pas encore une faute de type.
  3. Vérifiez la structure. Si le lexer passe, lancez parse et réparez le premier délimiteur, token ou expression attendue.
  4. Vérifiez les modules et les noms. Contrôlez space, les imports, la racine VITTE_MODULE_PATH et la visibilité des exports.
  5. Vérifiez les types et les appels. Lisez ensemble le type attendu, le type reçu, la signature de procédure et l’expression qui fournit l’argument.
  6. Vérifiez le support backend. Une syntaxe et un type acceptés peuvent atteindre un cas non généré par la cible. Consultez la matrice de support.
  7. Recommencez après chaque correction. Corrigez l’erreur la plus proche de sa cause, puis relancez exactement la même commande.
build/bin/vitte lex chemin/vers/main.vit
build/bin/vitte parse chemin/vers/main.vit
build/bin/vitte check chemin/vers/main.vit --diagnostic=terminal
build/bin/vitte compile chemin/vers/main.vit --stop-after-sema
build/bin/vitte compile chemin/vers/main.vit

Les étapes ne prouvent pas la même chose : un parse réussi confirme la structure reconnue ; il ne prouve ni la résolution de tous les symboles ni la génération d’un exécutable.

Les commandes reproduisent ces erreurs avec le compilateur local depuis la racine du dépôt. Les chemins et l’emplacement du soulignement sont dans la sortie ci-dessous ; ils peuvent varier si le fichier ou la version change.

Lexer — fermer le littéral concerné

Fixture : examples/diagnostics/unterminated_string.vit. Commande vérifiée :

build/bin/vitte check examples/diagnostics/unterminated_string.vit \
  --quiet --no-color --diagnostic=terminal

Résultat observé : code de sortie 1, code E0102, phase lexer, plage au début de la chaîne ouverte. Le correctif consiste à fermer le littéral avec le bon guillemet, ou à échapper un guillemet qui appartient au texte. Ne changez pas le type de la variable pour réparer un littéral lexical.

Parser — remettre le token attendu

Fixture : examples/diagnostics/syntax_missing_semicolon.vit. La dernière instruction est return 0 sans point-virgule. Commande vérifiée :

build/bin/vitte check examples/diagnostics/syntax_missing_semicolon.vit \
  --quiet --no-color --diagnostic=terminal

Résultat observé : E0201, expected token, attendu ; mais trouvé }. Ajoutez le point-virgule à la fin de return 0;. Le diagnostic est placé sur l’accolade, car c’est à cet endroit que le parser constate l’absence du token attendu.

Import — distinguer le chemin du nom exporté

Fixture : examples/diagnostics/missing_import.vit. Commande vérifiée :

build/bin/vitte check examples/diagnostics/missing_import.vit \
  --quiet --no-color --diagnostic=terminal

Résultat observé : E0301, phase import, chemin introuvable missing::package::module. Vérifiez dans cet ordre :

  1. le fichier qui correspond au chemin logique demandé ;
  2. la déclaration space du fichier fournisseur ;
  3. la racine de recherche configurée, par exemple VITTE_MODULE_PATH=examples ;
  4. la casse et l’orthographe de chaque segment ;
  5. l’export du symbole si le module est trouvé, mais pas le nom importé.

Pour comparer avec un import fonctionnel, voyez l’exemple multi-fichier du chapitre sur les modules. Une erreur de module introuvable se corrige par le chemin ou la racine ; une erreur de symbole privé se corrige par l’interface exportée.

Résolution des noms — déclarer, importer ou corriger la casse

Fixture : examples/diagnostics/unknown_name.vit. La procédure retourne missing_value sans qu’un tel nom soit visible dans la portée. Commande vérifiée :

build/bin/vitte check examples/diagnostics/unknown_name.vit \
  --quiet --no-color --diagnostic=terminal

Résultat observé : E0401, unknown symbol `missing_value`. Déclarez la valeur dans la portée, importez la déclaration depuis son module, ou corrigez le nom utilisé. Vérifiez aussi qu’une variable déclarée dans un bloc n’est pas utilisée après la fin de ce bloc.

const missing_value: i64 = 42;

proc main() -> i64 {
    return missing_value;
}

Types — lire ensemble l’opérateur et ses opérandes

Fixture : examples/diagnostics/invalid_not_operand.vit. L’opérateur logique not reçoit 1, dont le type est i64, alors qu’il attend un booléen. Commande vérifiée :

build/bin/vitte check examples/diagnostics/invalid_not_operand.vit \
  --quiet --no-color --diagnostic=terminal

Résultat observé : E0512, type attendu bool, type reçu i64. Si l’intention est de nier un test, écrivez une comparaison qui retourne un booléen, par exemple not (count > 0). Si vous vouliez vérifier un entier, utilisez une comparaison entière telle que count == 0. Convertir arbitrairement l’entier en booléen cacherait la question de sens du programme.

Appel — comparer la signature et les arguments

Fixture : examples/diagnostics/wrong_arity.vit. one attend un paramètre i64, mais main l’appelle sans argument. Commande vérifiée :

build/bin/vitte check examples/diagnostics/wrong_arity.vit \
  --quiet --no-color --diagnostic=terminal

Résultat observé : E0601, la procédure requiert un argument et aucun n’a été fourni. Passez la valeur attendue, par exemple one(42), ou corrigez la déclaration si le paramètre n’est pas nécessaire. Si le nombre est juste mais qu’un autre code apparaît, comparez aussi l’ordre et les types des arguments (E0602 désigne un type d’argument incompatible).

Backend — distinguer une limite de génération d’une faute de syntaxe

Le fichier examples/tutorials/generiques-limites.vit montre une construction générique qui atteint le backend. Commande vérifiée :

build/bin/vitte compile examples/tutorials/generiques-limites.vit \
  --emit-c --quiet --no-color --diagnostic=terminal

Résultat observé : E0902, C17 code generation failed, avec le détail indiquant que les formes génériques et contraintes where doivent être monomorphisées avant l’émission C17. Cette erreur ne signifie pas nécessairement que le fichier est mal formé : elle peut marquer une étape de génération absente pour cette construction.

Vérifiez la matrice de support avant de réécrire un programme. Si une forme équivalente plus simple est disponible et vérifiée, réduisez le cas ; sinon, fournissez un reproducer minimal dans une issue. Ne présentez pas un changement de syntaxe comme un correctif si c’est le backend qui manque.

Préparer un signalement reproductible

Si le diagnostic semble contredire le programme ou la prise en charge annoncée, fournissez un cas réduit et les informations qui déterminent le résultat :

  1. la version exacte de Vitte et l’origine du binaire ;
  2. la commande complète, les options et le répertoire courant ;
  3. le ou les fichiers minimums pour reproduire, en gardant leurs chemins de module ;
  4. la sortie complète, de préférence avec --no-color et le code de diagnostic ;
  5. la phase attendue et celle réellement observée ;
  6. le système et le compilateur C hôte si l’échec arrive au backend ou à la liaison.

Retirez secrets, jetons, adresses internes et données réelles. Recherchez ensuite les issues déjà ouvertes et créez un signalement si le cas est nouveau. Pour en savoir plus sur les commandes et les sorties machine, consultez la référence CLI.
