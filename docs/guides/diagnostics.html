Trouver l’explication d’un code

Conservez le code public affiché entre crochets, par exemple E0602. Il identifie la famille d’erreur et peut être recherché dans une issue ou expliqué directement par le compilateur :

vitte check src/main.vit --quiet --no-color
vitte explain E0602
vitte explain E0602 --diagnostic=json

vitte explain CODE affiche l’aide générale associée au code, alignée sur celle du diagnostic normal. Il accepte aussi le nom symbolique lorsqu’il est connu. Si le message dépend du code source, la sortie normale ajoute des informations comme le nom de la procédure, le type reçu ou la position du token ; explain donne le conseil applicable sans contexte de programme.

Lire les parties d’un diagnostic

  • Le titre et le code nomment le défaut. Le code public est utile pour les recherches et les rapports.
  • La phase indique l’étape qui a détecté le problème : lexer, parser, import, résolution de nom, types, constantes, backend ou liaison.
  • Le soulignement principal désigne l’expression, le nom ou le token en cause. Pour un délimiteur manquant, le curseur peut viser le point où le parser l’attend plutôt que le caractère absent.
  • Les valeurs attendue et reçue relient l’expression au contexte, comme le type exigé par un paramètre.
  • Les emplacements liés montrent une déclaration, un conflit, une origine d’import ou une autre source utile à la compréhension.
  • L’aide donne une prochaine action. Elle peut être adaptée à votre code et à la construction qui a échoué.

Corrigez d’abord le défaut le plus proche de sa cause, puis relancez la même commande. Un nom inconnu peut, par exemple, rendre les vérifications de son opérateur impossibles ; un diagnostic ultérieur peut alors dépendre du premier.

Choisir une correction adaptée à l’intention

Erreur de syntaxe

Suivez le token attendu et vérifiez les délimiteurs depuis leur ouverture. Pour un appel, une parenthèse qui manque doit être ajoutée à la liste d’arguments correspondante, pas à la prochaine expression voisine. Si plusieurs erreurs indépendantes sont affichées, corrigez-les dans l’ordre source et relancez le compilateur après les changements de structure.

Type ou appel incompatible

Comparez le type attendu, le type reçu, la signature et l’expression concernée. Dans cet exemple, le paramètre de add attend un entier :

proc add(value: i64) -> i64 { return value; }
proc main() -> i64 { return add("42"); }

Si la chaîne représente une donnée textuelle, changez la signature et le traitement de add selon cette intention. Si la valeur doit être numérique, fournissez une valeur de type entier après avoir choisi comment traiter la conversion. Le diagnostic ne peut pas choisir cette décision à votre place.

Module ou nom introuvable

Vérifiez séparément le chemin logique du module, les racines de recherche, la déclaration space, l’orthographe du symbole et son export. VITTE_MODULE_PATH ajoute des racines ; le dossier courant choisit le projet chargé par le CLI natif 0.1.1. Ces réglages ne rendent pas visible un nom privé. Consultez le dépannage des imports pour les vérifications détaillées.

Limite de backend ou de cible

Un diagnostic de backend ou de liaison peut signaler une fonctionnalité non prise en charge, une incompatibilité de cible ou un outil externe en échec. Gardez la commande complète, la cible demandée, la phase du message et la sortie de l’outil. Vérifiez ensuite la matrice de support avant de réécrire une construction acceptée par le frontend.

Suggestions et changements automatiques

Une proposition marquée machine-applicable décrit un remplacement précis que l’outil peut appliquer sans inventer un choix de programme. Les mentions manual, maybe-incorrect ou has-placeholders indiquent une piste à examiner, pas une modification sûre. Une correction qui change le comportement, la visibilité, l’ownership ou les garanties de sécurité demande un choix explicite du développeur.

Une suggestion de nom n’est utile que si un seul symbole visible correspond de façon suffisamment proche. En l’absence de proposition, recherchez le nom ou vérifiez ses imports et sa portée au lieu d’inventer une correction.

Sorties pour terminal, outils et éditeurs

Le terminal est le format le plus lisible pour corriger le programme. Les formats machine peuvent transporter plusieurs diagnostics dans un seul document :

vitte check src/main.vit --quiet --no-color --diagnostic=json
vitte check src/main.vit --quiet --no-color --diagnostic=sarif

JSON convient aux scripts et conserve les codes, phases, sévérités, informations de type et emplacements exposés par la version du compilateur. SARIF sert aux outils d’analyse de code qui lisent SARIF 2.1.0. LSP est destiné aux intégrations de langage qui consomment des plages de source et des informations liées ; utilisez --diagnostic=lsp avec un client LSP compatible.

Les sorties terminal, JSON, SARIF et LSP représentent le même défaut sous des schémas différents. Un outil peut afficher les annotations ou les aides différemment ; pour le contenu complet, gardez aussi la sortie de vitte explain CODE.

Plusieurs diagnostics et récupération

Quand il peut reprendre sans fabriquer d’arbre syntaxique trompeur, le compilateur continue après une erreur pour montrer des défauts indépendants plus loin dans le fichier. Une récupération sûre conserve leur ordre d’apparition dans le programme. Une erreur lexicale ou syntaxique qui empêche de déterminer la structure peut toutefois masquer les erreurs suivantes ; le nombre de diagnostics ne garantit pas que tout le fichier a été analysé.

Une erreur peut entraîner des messages secondaires dans une étape ultérieure. Traitez la première cause qui invalide une expression ou une déclaration, puis relancez la vérification. Si le compilateur s’arrête, se répète ou produit un message interne au lieu de signaler le défaut source, réduisez le cas avant d’en tirer une conclusion.

Partager un problème reproductible

Pour un diagnostic inattendu ou une erreur du compilateur, incluez la version, la commande complète, le répertoire de lancement, le plus petit fichier ou ensemble de modules qui reproduit le cas, ainsi que la sortie intégrale avec --no-color. Pour un souci d’éditeur, ajoutez la version de Vitte, l’éditeur et le client utilisés. Retirez secrets et données confidentielles.

Le guide des erreurs reproduites détaille les codes fréquents. La référence CLI décrit les commandes et options ; la matrice de support distingue les constructions analysées de celles validées jusqu’à l’exécution.
