Version publiée et version des sources sont deux informations différentes.

État relevé le 28 octobre 2026 : la dernière release publique consultée du compilateur Vitte indique le paquet 0.1.0, tandis que le fichier VERSION de cette copie du dépôt indique 0.1.1. Le numéro 0.1.1 décrit donc ici les sources vérifiées ; il ne signifie pas qu’une release binaire portant ce numéro est déjà publiée. Consultez toujours les releases officielles avant de télécharger un artefact.

Release Vitte 2026.10 — paquet 0.1.0

La release publique VersionOctobre2026 a été publiée le 3 octobre 2026 et annonce le paquet Vitte 0.1.0. Sa note de version rassemble les composants livrés avec cette publication. Elle constitue un état de release daté : elle ne remplace pas les tests ni la matrice de support d’une copie plus récente du dépôt.

  • Lire la note officielle Vitte 2026.10 pour les détails et les artefacts joints.
  • La page d’installation et dépannage distingue les fichiers réellement publiés des formats que des scripts savent éventuellement fabriquer.
  • La matrice de support indique les constructions vérifiées par le dépôt ; une note de release ne garantit pas chaque forme de la grammaire.

État des sources Vitte 0.1.1

Le dépôt de travail actuellement décrit par cette documentation porte 0.1.1 dans VERSION et dans le manifeste de la copie intégrée du module JSON. Les changements ci-dessous sont ceux établis par les sources et les vérifications du dépôt ; ils ne doivent pas être présentés comme une liste d’artefacts d’une release publiée tant que la page Releases ne l’indique pas.

Module JSON

  • Les profils de limites du lexer et du parser sont exposés : valeurs par défaut, constructeurs contrôlés et fonctions de validation.
  • Les points d’entrée parse_with_limits, parse_strict_with_limits et parse_tokens_with_limits acceptent des limites explicites. Le parsing strict impose le rejet des clés d’objet répétées.
  • Les résultats de parsing exposent leur diagnostic via JsonParseResult.report. Lorsqu’un parsing depuis le texte échoue au lexer, le résultat du parser conserve le détail et la plage source et classe l’erreur comme flux de tokens invalide.
  • La suite du module vérifie les plafonds de profondeur, de valeurs, de membres, de clés, de tokens, de chaînes, de nombres et de taille de source, y compris leurs frontières.

Compilateur et intégration

  • Une addition dont les deux opérandes HIR sont des chaînes est abaissée vers l’opération IR de concaténation de chaînes. La régression du consommateur JSON compile et s’exécute sur le bootstrap courant.
  • La cible test-ir-backend suit désormais le programme Vitte maintenu du dépôt au lieu de dépendre d’un ancien harnais C absent.
  • Le contrôle de release du compilateur et make -C modules/json verify ont réussi sur la copie de travail examinée le 28 octobre 2026. Cette preuve porte sur ce commit et ces cibles, pas sur une future release ou toutes les constructions du langage.

Migrer le code consommateur JSON

Le changement d’accès le plus visible pour un consommateur qui passe de la version JSON publiée 0.1.0 à l’API présente dans la copie du dépôt 0.1.1 concerne le champ de diagnostic. Les anciennes sources utilisaient JsonParseResult.diagnostic ; la forme actuelle expose JsonParseResult.report.

Adaptation de source

Recherchez les accès à .diagnostic sur un JsonParseResult et remplacez-les par .report. Les diagnostics du lexer ont leur propre forme : ne renommez pas leurs champs sans vérifier le type importé.

// Ancien accès dans une copie du module JSON 0.1.0
if not parsed.ok {
    print(parsed.diagnostic.message);
    return 1;
}

// Accès dans le module JSON 0.1.1 du dépôt Vitte
if not parsed.ok {
    print(parsed.report.message);
    return 1;
}

Les entrées courantes parse, parse_strict, parse_tokens et parse_tokens_strict restent les choix simples lorsque les limites par défaut conviennent. Pour rendre les ressources explicites, importez les profils et choisissez le point d’entrée correspondant :

use json::lexer::lexer::{
    JsonLexerLimits,
    default_lexer_limits,
    new_lexer_limits,
};
use json::parser::parser::{
    JsonParserLimits,
    JsonParserDuplicateKeyPolicy,
    default_parser_limits,
    new_parser_limits,
    parse_with_limits,
    parse_strict_with_limits,
};

let lexer_limits: JsonLexerLimits = default_lexer_limits();
let parser_limits: JsonParserLimits = default_parser_limits();
let result = parse_with_limits(source, lexer_limits, parser_limits);

// Pour des données non fiables et des clés uniques :
let strict_limits: JsonParserLimits = new_parser_limits(
    64, 50000, 10000, 10000, 4096,
    JsonParserDuplicateKeyPolicy.Reject);
let strict_result = parse_strict_with_limits(
    source, lexer_limits, strict_limits);

Les cinq nombres de new_parser_limits règlent, dans l’ordre, la profondeur, le nombre total de valeurs, les éléments par tableau, les membres par objet et la longueur des clés. La longueur de clé est mesurée après décodage. Les nombres doivent être strictement positifs. parse_with_limits respecte la politique de doublons reçue ; la variante strict force Reject.

Pour un fichier ou un corps HTTP, bornez également la lecture avant de créer la chaîne passée au lexer.

Vérifier une mise à jour dans son projet

  1. Notez la version du binaire avec build/bin/vitte --version ou vitte --version.
  2. Notez le dépôt et la version de chaque module dans son package.toml.
  3. Recherchez les champs de résultat, les fonctions d’import et les options que le projet utilise réellement.
  4. Vérifiez d’abord les sources puis l’intégration installée avec make -C modules/json check et make -C modules/json verify.
  5. Relancez ensuite les commandes propres à votre application et comparez leurs sorties avec les résultats attendus.

Une compilation réussie ne garantit pas que la règle métier de l’application soit correcte. Après parsing, vérifiez les types JSON, les champs obligatoires et les plages métier avant d’utiliser ou d’encoder la valeur.
