Exemple exécuté avec le bootstrap Vitte 0.1.1.

Le programme et la commande de cette page ont été vérifiés le 28 octobre 2026 depuis la racine du dépôt. Le document JSON est stocké dans une chaîne source : ce projet démontre le parsing et la validation, pas l’ouverture d’un fichier ou la lecture de stdin.

Objectif et contrat du programme

Le programme reçoit un document décrivant un service. Il refuse un JSON mal formé, rejette les clés dupliquées, exige un objet racine contenant une clé service, puis vérifie que cet objet contient un nom, un port entier et un indicateur booléen. Le port doit se trouver dans la plage TCP habituelle 1..65535. Si tout est valide, le programme affiche un résumé puis le document réencodé avec indentation.

La validation se déroule en couches distinctes. parse_strict contrôle la syntaxe JSON et l’unicité des clés. Le code Vitte contrôle ensuite le schéma métier. Le succès du parseur ne garantit donc pas qu’un port existe, qu’il soit entier ou qu’il soit valide pour l’application.

{
  "service": {
    "name": "gateway",
    "port": 8443,
    "enabled": true
  }
}

Il faut un build du dépôt Vitte et les sources du module JSON à l’emplacement modules/json. Le programme importe trois espaces : json::parser::parser pour lire, json::core::value pour inspecter, et json::encode::encoder pour réécrire.

Étape 1 : importer uniquement les fonctions nécessaires

Les imports groupés indiquent la provenance des types et fonctions. Ils évitent un glob qui rendrait moins évident le module propriétaire de chaque nom :

use json::core::value::{
    JsonValue,
    bool_or,
    integer_or,
    is_bool,
    is_integer,
    is_object,
    is_string,
    object_get_ref,
    object_len,
    object_member_ref,
    string_or,
};
use json::encode::encoder::{JsonEncodeResult, encode_pretty};
use json::parser::parser::{JsonParseResult, parse_strict};

JsonValue est le nœud de l’arbre JSON. Les prédicats is_object, is_string, is_integer et is_bool vérifient les formes reçues avant les conversions. Les fonctions integer_or, string_or et bool_or donnent une valeur de repli ; ici elles suivent la vérification de type, de sorte que ce repli ne masque pas une entrée de type incorrect.

Étape 2 : vérifier les clés avant d’obtenir une référence

object_get_ref est un accès direct : il exige que la valeur soit un objet et que la clé existe. La procédure object_has parcourt les membres grâce à object_len et object_member_ref. Elle permet de vérifier les préconditions avant d’appeler l’accès direct.

proc object_has(object: &JsonValue, wanted: string) -> bool {
    if not is_object(object) {
        return false;
    }

    let mut index: usize = 0;
    while index < object_len(object) {
        let member = object_member_ref(object, index);
        if member.key == wanted {
            return true;
        }
        set index += 1;
    }

    return false;
}

Cette fonction ne construit pas de nouvelle valeur JSON et ne modifie pas l’objet ; elle cherche seulement une clé. Une fois object_has vrai, object_get_ref fournit une référence vers la valeur existante.

Étape 3 : parser en mode strict

Le texte est donné comme chaîne et passé à parse_strict. Ce mode traite les clés dupliquées comme une erreur. En cas d’échec, parsed.ok est faux et parsed.report contient le diagnostic de la version 0.1.1 du module JSON.

let source: string =
    "{\"service\":{\"name\":\"gateway\",\"port\":8443,\"enabled\":true}}";

let parsed: JsonParseResult = parse_strict(source);
if not parsed.ok {
    print("Erreur : le document JSON est invalide.");
    return 1;
}

Pour afficher le détail technique pendant le développement, remplacez le message générique par parsed.report.message ou examinez les champs de JsonParserDiagnostic. En production, évitez d’exposer à un utilisateur final des chemins système ou des données sensibles inclus dans un diagnostic.

Étape 4 : valider la forme et les champs

Le document doit d’abord être un objet. Le champ service doit exister et être un objet lui aussi. Le programme vérifie ensuite la présence des trois champs requis avant de demander leurs références :

let root: &JsonValue = &parsed.value;
if not is_object(root) or not object_has(root, "service") {
    return 2;
}

let service: &JsonValue = object_get_ref(root, "service");
if not is_object(service) {
    return 3;
}

if not object_has(service, "name") or
   not object_has(service, "port") or
   not object_has(service, "enabled") {
    return 4;
}

Les codes de retour rendent les étapes distinctes dans un script ou un test d’intégration. Le programme affiche aussi un message adapté avant chaque retour. Dans une application plus grande, on pourrait remplacer ces entiers par un type d’erreur métier, si les constructions utilisées sont prises en charge par la cible choisie.

Étape 5 : contrôler les types et les règles métier

JSON n’a qu’une catégorie générale « number », mais le modèle du module distingue les entiers et les flottants. Le port est volontairement exigé comme entier : 8443.0 est donc rejeté par cette règle, même si sa valeur mathématique est entière.

let name: &JsonValue = object_get_ref(service, "name");
let port: &JsonValue = object_get_ref(service, "port");
let enabled: &JsonValue = object_get_ref(service, "enabled");

if not is_string(name) or not is_integer(port) or not is_bool(enabled) {
    return 5;
}

let service_name: string = string_or(name, "");
let service_port: i64 = integer_or(port, 0);
let service_enabled: bool = bool_or(enabled, false);

if service_name.length == 0 or
   service_port < 1 or service_port > 65535 {
    return 6;
}

Le domaine réseau définit les ports utilisables de 1 à 65535. Cette règle appartient au programme, pas à JSON : un nombre peut être valide JSON tout en étant impossible à utiliser comme port. La valeur 0 est réservée ici au repli après conversion et est ensuite rejetée par le contrôle de plage.

Étape 6 : réencoder seulement après validation

Après avoir vérifié le schéma et l’activation du service, le programme appelle encode_pretty. Il vérifie encore ok avant d’afficher text. L’encodeur reçoit l’arbre JSON d’origine : il reformate le document, mais ne remplace pas la validation métier.

let encoded: JsonEncodeResult = encode_pretty(&parsed.value);
if not encoded.ok {
    return 8;
}

print("Configuration valide : gateway écoute sur le port 8443.\n");
print(encoded.text);
return 0;

Fichier complet

Le fichier complet exécutable est examples/projects/json_config/main.vit. Le voici en entier pour pouvoir le lire sans quitter le guide :

space projects::json_config::main;

use json::core::value::{
    JsonValue,
    bool_or,
    integer_or,
    is_bool,
    is_integer,
    is_object,
    is_string,
    object_get_ref,
    object_len,
    object_member_ref,
    string_or,
};
use json::encode::encoder::{
    JsonEncodeResult,
    encode_pretty,
};
use json::parser::parser::{
    JsonParseResult,
    parse_strict,
};

proc object_has(object: &JsonValue, wanted: string) -> bool {
    if not is_object(object) {
        return false;
    }

    let mut index: usize = 0;
    while index < object_len(object) {
        let member = object_member_ref(object, index);
        if member.key == wanted {
            return true;
        }
        set index += 1;
    }

    return false;
}

proc main() -> int {
    let source: string =
        "{\"service\":{\"name\":\"gateway\",\"port\":8443,\"enabled\":true}}";

    let parsed: JsonParseResult = parse_strict(source);
    if not parsed.ok {
        print("Erreur : le document JSON est invalide.");
        return 1;
    }

    let root: &JsonValue = &parsed.value;
    if not is_object(root) or not object_has(root, "service") {
        print("Erreur : la clé service doit contenir un objet.");
        return 2;
    }

    let service: &JsonValue = object_get_ref(root, "service");
    if not is_object(service) {
        print("Erreur : service doit être un objet.");
        return 3;
    }

    if not object_has(service, "name") or
       not object_has(service, "port") or
       not object_has(service, "enabled") {
        print("Erreur : name, port et enabled sont obligatoires.");
        return 4;
    }

    let name: &JsonValue = object_get_ref(service, "name");
    let port: &JsonValue = object_get_ref(service, "port");
    let enabled: &JsonValue = object_get_ref(service, "enabled");

    if not is_string(name) or not is_integer(port) or not is_bool(enabled) {
        print("Erreur : name, port et enabled ont des types incorrects.");
        return 5;
    }

    let service_name: string = string_or(name, "");
    let service_port: i64 = integer_or(port, 0);
    let service_enabled: bool = bool_or(enabled, false);

    if service_name.length == 0 or
       service_port < 1 or service_port > 65535 {
        print("Erreur : nom vide ou port hors de la plage 1..65535.");
        return 6;
    }

    if not service_enabled {
        print("Erreur : ce guide attend un service activé.");
        return 7;
    }

    let encoded: JsonEncodeResult = encode_pretty(&parsed.value);
    if not encoded.ok {
        print("Erreur : l’encodeur n’a pas pu produire le JSON.");
        return 8;
    }

    print("Configuration valide : gateway écoute sur le port 8443.\n");
    print(encoded.text);
    return 0;
}

Exécuter le projet et comparer la sortie

Depuis la racine du dépôt, ajoutez au chemin de recherche la racine des exemples et celle qui contient le namespace json. La commande testée sur Unix/macOS est :

VITTE_MODULE_PATH="$PWD/examples:$PWD/modules" \
  build/bin/vitte run examples/projects/json_config/main.vit \
  --quiet --no-color

Résultat confirmé : code de sortie 0 et sortie standard suivante :

Configuration valide : gateway écoute sur le port 8443.
{
  "service": {
    "name": "gateway",
    "port": 8443,
    "enabled": true
  }
}

Sur Windows, définissez VITTE_MODULE_PATH avec le séparateur de chemins ; et utilisez l’exécutable de la distribution Windows. La chaîne exacte de lancement dépend du terminal et de l’emplacement choisi pour le dépôt.

Comportements d’erreur et codes de sortie

CodeConditionAction du programme
0JSON syntaxiquement valide, schéma satisfait, service activé, encodage réussi.Affiche le résumé et la configuration réindentée.
1parse_strict renvoie ok = false.Refuse le document avant d’accéder à l’arbre.
2La racine n’est pas un objet ou la clé service manque.Refuse la configuration sans appeler un accès objet invalide.
3service existe, mais n’est pas un objet.Refuse un mauvais type racine du sous-document.
4Une des clés name, port ou enabled manque.Signale les champs requis absents.
5Un des trois champs a un type JSON incorrect.Exige chaîne, entier et booléen dans cet ordre.
6Le nom est vide ou le port sort de 1..65535.Applique les contraintes métier propres à ce programme.
7Le service est désactivé.Refuse l’état demandé par ce scénario.
8L’encodeur ne produit pas de résultat valide.Ne lit pas la sortie de l’encodeur en échec.

Limites de ce projet et prolongements documentés

  • Pas d’entrée fichier : source est une chaîne embarquée. Le module JSON ne lit ni fichier ni stdin ; une couche d’E/S doit fournir les octets et imposer sa propre limite avant de créer la chaîne.
  • Schéma volontairement étroit : cet exemple vérifie trois champs d’un objet précis. Une configuration réelle peut nécessiter des champs facultatifs, des valeurs par défaut, des chemins imbriqués et des diagnostics métier distincts.
  • Accès par référence : vérifiez le type de l’objet et l’existence de la clé avant object_get_ref, qui suppose ces conditions.
  • Budgets de parsing : pour des données non fiables, utilisez les variantes à limites décrites dans le guide de migration et la référence JSON.
  • Compatibilité du langage : un exemple qui s’exécute sur cette version ne prouve pas le support de toutes les formes Vitte. La matrice de support reste la référence par construction.
