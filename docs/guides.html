Les commandes dépendent des capacités réellement disponibles

Les instructions de construction ci-dessous suivent le README du dépôt. La compilation de bout en bout dépend du sous-ensemble pris en charge par le frontend et le backend employés. Consultez la matrice de support pour lire les preuves construction par construction.

Installer ou construire le compilateur

Le parcours de construction principal du dépôt consiste à récupérer les sources puis à construire le compilateur avec make. Prévoyez un compilateur C17 et l’outil make.

git clone https://github.com/vitte-lang/vitte.git
cd vitte
make
./build/bin/vitte --version

La construction place le binaire dans build/bin/vitte. Après installation dans un préfixe, vous pouvez appeler vitte si le dossier bin de ce préfixe figure dans PATH. Le dépôt documente aussi une construction avec CMake :

cmake -S . -B build
cmake --build build

Les paquets distribués, les scripts d’installation et les plateformes prises en charge évoluent avec le projet. Consultez les versions publiées et le README à jour avant de choisir un paquet.

Organiser les sources d’un projet

Un petit programme peut tenir dans un fichier .vit. Sa déclaration de module, ses imports et ses procédures donnent au compilateur les noms et les chemins logiques employés dans le code. À mesure que le programme grandit, gardez cohérents le chemin space, les noms des fichiers, les imports et la racine à partir de laquelle vous lancez la commande.

space application/main;

proc main() -> int {
    return 0;
}

Pour les modules, la CLI documente --project-root, --manifest-path et la variable VITTE_MODULE_PATH. Cette dernière ajoute des racines de recherche pour les modules ; elle ne remplace pas la déclaration des chemins et imports dans les fichiers source.

VITTE_MODULE_PATH="$PWD/modules" build/bin/vitte compile application.vit -o application
vitte check src/main.vit

Le module JSON du dépôt illustre un paquet organisé avec package.toml. Ce manifeste décrit ce paquet et son point d’entrée ; il ne faut pas le confondre avec un gestionnaire universel de dépendances ou un format de projet garanti pour toutes les applications. La page Modules et visibilité détaille la résolution documentée et ses limites.

Vérifier et compiler un programme

Les commandes courtes permettent de localiser la phase concernée. Lancez-les depuis la racine de votre dépôt ou précisez explicitement le chemin du fichier.

vitte lex examples/hello.vit
vitte parse examples/hello.vit
vitte check examples/hello.vit
vitte compile examples/hello.vit --stop-after-sema
vitte compile examples/hello.vit
vitte run examples/hello.vit
  • lex affiche ou vérifie la lecture des tokens.
  • parse contrôle la structure syntaxique reconnue par le parseur.
  • check lance les vérifications exposées par le frontend sélectionné.
  • compile --stop-after-sema demande un arrêt après l’analyse sémantique.
  • compile et run demandent les étapes de backend et d’exécution lorsque la construction et le chemin sélectionnés les prennent en charge.

Ne déduisez pas qu’un programme complet est pris en charge parce que ses mots sont présents dans l’EBNF ou parce que son analyse syntaxique réussit. Utilisez l’index des commandes pour les options, puis la matrice de support pour les preuves de compilation et d’exécution. Les tests du dépôt peuvent être lancés avec make test.

Comprendre les erreurs et dépanner

Un diagnostic est plus utile lorsqu’il est rattaché à l’étape exacte où le compilateur s’arrête. Reprenez le programme dans l’ordre : fichier et commande employés, tokens, structure, noms et types, génération, puis exécution. Une erreur observée tard dans le pipeline peut être causée par une hypothèse invalide faite plus tôt.

  1. Vérifiez la commande et le fichier. Confirmez que le binaire attendu est lancé, que le chemin existe et que vous partez de la bonne racine de projet.
  2. Réduisez la phase. Utilisez lex, parse, check ou compile --stop-after-sema pour repérer le premier stade qui échoue.
  3. Vérifiez les noms et les modules. Comparez space, les chemins use, les noms de fichier, les exports et les racines données à VITTE_MODULE_PATH ou --project-root.
  4. Vérifiez le niveau de support. Une construction peut être reconnue par un parseur, puis rejetée par l’analyse sémantique ou le backend. Cherchez-la dans la fiche concernée et dans la matrice de support.
  5. Conservez les éléments utiles. Notez la version, la commande exacte, le diagnostic complet et le plus petit fichier source qui reproduit le problème.

Pour les détails des codes, formats de sortie et options d’arrêt, consultez CLI et diagnostics. Si le problème n’est pas déjà signalé, ouvrez une issue sur le dépôt avec les éléments de reproduction.
