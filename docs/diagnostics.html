Vitte Diagnostics

Quick consultation of diagnostics: a code, a layer, a correction.

Source of truth

The default CLI uses the C17 implementation in src/bootstrap/diagnostic/. The staged Vitte implementation lives in src/compiler/diagnostic/, with its diagnostic model in src/compiler/diagnostic/diagnostic.vitte. The shared reference is Compiler Diagnostics (source: docs/compiler/diagnostics.md); the retired diagnostics migration is documented in secondary project resources.

Official sequence

  • vitte check <file> validates a file without code generation.
  • vitte check <file> --diagnostic=json emits diagnostics as JSON. The alias is --diagnostic-format=json.
  • vitte explain E0501 --diagnostic=json explains one public diagnostic code as JSON.
  • vitte parse <file> --emit-ast parses a file and prints an AST summary.
  • vitte compile <file> --emit-hir and vitte compile <file> --emit-ir expose intermediate output.
  • vitte run <file> compiles and runs a program.

These command and option spellings are defined in src/bootstrap/cli/command_spec.def. Use src/tests/diagnostic_sema_multiple_invalid.vit from the repository root to reproduce semantic type errors.

Stable JSON surface

  • schema is "vitte-diagnostics".
  • version is the JSON schema version (currently 1).
  • counts summarizes severities; stored gives the number of stored entries.
  • diagnostics[] contains the structured diagnostic records.

Phase map

  • frontend : lexer, parser, ast_validation
  • resolution : module_resolution, symbol_resolution, sema
  • middle-end : hir, typeck, borrowck, mir, mir_lowering, mir_verification, ir
  • backend : backend, linker, runtime_execution
  • driver : CLI/input/configuration failures before or around the pipeline

Frequent codes

  • PARSE_E_UNCLOSED_BLOCK - parser reached EOF before a closing delimiter
  • E1005 - unknown identifier
  • TYPECK_E_ASSIGN_MISMATCH - assignment type mismatch
  • BORROWCK_E_USE_AFTER_MOVE - moved value used later
  • LIMIT_FILE_SIZE_MAX - source exceeds hard input-size policy

What to do first

  • Read the first failing phase and code, not the whole waterfall.
  • Reduce the repro to the smallest file that still fails.
  • Re-run with --diagnostic=json when you need machine-readable detail.
  • Use --emit-ast, --emit-hir, or --emit-ir only when the earlier phase has progressed far enough to produce that representation.

Quick index

  • parse : malformed syntax, recovery diagnostics, unclosed delimiters.
  • resolve : missing modules, symbols, visibility and name binding issues.
  • typeck : incompatible assignments, call arity/type mismatches, non-exhaustive matches.
  • borrowck : use-after-move, borrow conflicts, lifetime failures.
  • driver : invalid CLI input, path/policy issues, hardening limits.

Example

vitte check src/tests/diagnostic_sema_multiple_invalid.vit --diagnostic=json

This command uses a tracked fixture with two semantic type errors. Run it from the repository root, then reduce your own repro to the smallest source file that still fails.

Practical reading

Diagnostics should be read as a contract, not as a wall of text. The phase tells you where the pipeline stopped, the code names the stable failure class, and the JSON envelope lets you inspect the same event without scraping text output.

For a fast triage, use this order:

  1. Read the first diagnostic's phase and code fields.
  2. Read the primary code, message, label, note, and help.
  3. Reduce the repro to the smallest snippet that still fails.
  4. Re-run with --diagnostic=json if you need structured fields.
  5. Only then request AST/HIR/IR output if the failing phase is past parsing.

That sequence keeps bug reports useful: the report should name the phase, the code, the smallest repro, and the expected behavior instead of only describing the symptom.

If you need a broader starting point, read Documentation for the compiler surface and Source for the implementation path.
