Quatre questions pour chaque construction

Quand tu découvres une syntaxe, ne demande pas seulement « est-ce que le langage l’autorise ? ». Dans le dépôt Vitte, réponds à quatre questions distinctes :

  1. La grammaire la décrit-elle ? Une règle EBNF indique la forme prévue du code.
  2. L’analyseur l’accepte-t-il ? Le parseur peut reconnaître cette forme et construire une représentation.
  3. L’analyse sémantique la valide-t-elle ? Les noms, types et contraintes doivent aussi être cohérents.
  4. Le backend la compile-t-il et le programme s’exécute-t-il ? La preuve la plus concrète est un test qui construit un exécutable et vérifie son résultat.

Ces réponses ne sont pas interchangeables. Une page de grammaire décrit la syntaxe ; une commande de parsing confirme la structure ; un exécutable réussi confirme un cas précis sur un chemin de compilation donné.

Comparer des niveaux de preuve

La matrice du projet donne des exemples concrets. Une boucle while apparaît dans les tests runtime ; le compilateur natif la prend donc en charge dans les cas couverts. La déclaration d’une form non générique et le choix pick avec charge utile sont également exercés jusqu’à l’exécution.

À l’inverse, le test dédié d’une forme générique arrive jusqu’au backend, puis reçoit un diagnostic de génération de code. La forme for sur tableau atteint elle aussi une erreur backend dans le test ciblé. Ces exemples ne signifient pas que toute la syntaxe correspondante est inconnue : ils indiquent précisément que le chemin de compilation testé n’achève pas ces cas.

Consulte l’état du support Vitte avant de bâtir un projet sur une construction avancée. La matrice détaille aussi les différences entre le frontend natif et le chemin de compatibilité.

Explorer une source avec la CLI

Depuis la racine du dépôt, la CLI permet d’inspecter différentes étapes :

build/bin/vitte lex examples/tutorials/syntaxe.vit
build/bin/vitte parse examples/tutorials/syntaxe.vit
build/bin/vitte check examples/tutorials/syntaxe.vit
build/bin/vitte run examples/tutorials/syntaxe.vit --quiet --no-color

lex montre les tokens ; parse vérifie la structure ; check poursuit l’analyse ; run demande la compilation et l’exécution. Pour examiner une étape intermédiaire d’une compilation, la commande documentée accepte aussi compile fichier.vit --stop-after-sema. La disponibilité d’une option ne garantit pas la prise en charge de chaque syntaxe : note la commande et son résultat exact.

Réduire un problème à son plus petit exemple

Si un programme ne passe pas, enlève temporairement tout ce qui n’est pas nécessaire au diagnostic. Garde une seule déclaration, une procédure courte et la construction en question. Puis avance étape par étape :

  1. Vérifie que le fichier et la commande ciblent bien le même frontend.
  2. Exécute le parseur pour séparer un problème de syntaxe d’un problème plus loin dans le pipeline.
  3. Lis le code de diagnostic et l’emplacement, puis corrige une seule cause.
  4. Si le parsing et l’analyse passent mais que la génération échoue, compare à un exemple compilé du même type de construction.
  5. Ajoute le cas réduit aux notes de projet avec la version de l’outil et le résultat observé.

Une erreur backend n’est pas la preuve que ta syntaxe est mal écrite. Un diagnostic de type ne se corrige pas nécessairement en changeant la grammaire. Identifier la phase te permet de chercher au bon endroit.

Ne pas transformer un cas réussi en promesse générale

Si while fonctionne dans un exemple, cela confirme les opérations exercées dans cet exemple : la condition, le corps, les mises à jour et la sortie testée. Cela ne prouve pas automatiquement que toutes les formes de boucle, tous les types d’indice ou toutes les cibles d’exécution se comportent de la même façon.

Utilise la même précision quand tu écris de la documentation. Indique la source, la commande, le résultat et le mode de compilation. Si aucun test ne couvre le cas exact, dis qu’il reste à confirmer. Une limite documentée est plus utile qu’une promesse fondée uniquement sur la grammaire.

Atelier final : enquêter sur une fonctionnalité Vitte

  1. Choisis while, pick, une forme générique ou for.
  2. Ouvre la grammaire Vitte et trouve la règle ou note son absence.
  3. Consulte la matrice du compilateur et repère le test qui donne la meilleure preuve.
  4. Écris une note en quatre lignes : syntaxe décrite, acceptation, compilation, exécution.
  5. Si la commande ou le résultat ne sont pas clairs, réduis le cas et compare-le à une fixture existante.
Auto-évaluation

Une bonne note ne conclut pas seulement « pris en charge » ou « non pris en charge ». Elle nomme le chemin testé et le niveau atteint. Par exemple : « syntaxe décrite ; test ciblé reçu par le backend ; génération rejetée ; exécution non établie ».

Tu as terminé le parcours approfondi

Tu sais maintenant lire du code Vitte, raisonner sur ses valeurs et ses états, organiser ses modules et vérifier la prise en charge d’une forme avant de l’utiliser. Pour continuer, choisis une notion précise dans la référence, puis cherche une fixture correspondante dans le dépôt.
