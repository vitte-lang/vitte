Regrouper des champs avec form

Une forme déclare un type composé. Elle rassemble plusieurs champs sous un seul nom :

form Point {
    x: i64,
    y: i64,
}

proc distance_manhattan(point: Point) -> i64 {
    return point.x + point.y;
}

Le type Point évite de transporter séparément une coordonnée horizontale et une coordonnée verticale. Les noms des champs documentent leur rôle. Le corps peut y accéder avec la notation pointée, par exemple point.x.

On construit une valeur de forme en donnant les champs par leur nom :

proc exemple() -> i64 {
    let point: Point = Point {
        x: 12,
        y: 8,
    };
    return distance_manhattan(point);
}

Cette construction rend l’ordre des données sans importance pour le lecteur et évite les appels remplis de nombres sans étiquette. Pour une forme imbriquée, un champ peut lui-même recevoir une valeur construite d’un autre type.

Les formes gardent ensemble des données cohérentes

Imagine un rectangle défini par un coin minimum et un coin maximum. Deux champs de type Point expriment directement le modèle :

form Rectangle {
    minimum: Point,
    maximum: Point,
}

proc largeur(rectangle: Rectangle) -> i64 {
    return rectangle.maximum.x - rectangle.minimum.x;
}

Quand plusieurs procédures reçoivent les mêmes groupes de paramètres, c’est souvent le signe qu’une forme pourrait donner un nom à ce groupe. Mais n’ajoute pas un nouveau type juste pour envelopper une valeur sans règle ni sens supplémentaire : un nom utile exprime une idée du domaine.

Représenter des états avec pick

Une déclaration pick énumère des variantes possibles. Choisir entre ces variantes signifie qu’une valeur est dans un état parmi plusieurs :

pick Etat {
    Nouveau,
    EnCours,
    Termine,
}

proc est_actif(etat: Etat) -> bool {
    return etat == Etat.EnCours;
}

Une variante peut également porter des types dans ses parenthèses selon la grammaire, comme Erreur(i64). Cette forme suggère qu’une variante peut contenir une information associée. Avant de baser un programme sur une variante porteuse de données, vérifie les constructions et les accès réellement pris en charge dans le compilateur utilisé.

Exemple vérifié : champs de forme et charge utile de pick

examples/tutorials/formes-choix.vit additionne les champs d’un point et extrait le nombre porté par la variante Ok.

build/bin/vitte run examples/tutorials/formes-choix.vit --quiet --no-color

Résultat confirmé avec le frontend natif : code de sortie 0.

Choisir entre une forme et un choix

Pose-toi la question suivante : est-ce que mon objet possède plusieurs propriétés en même temps, ou est-il dans un état parmi plusieurs ? Un compte a probablement un identifiant, un nom et un solde à la fois : c’est une bonne candidate pour une form. Une opération est soit en attente, soit réussie, soit échouée : c’est souvent un pick.

Un état explicite empêche des combinaisons invalides. Trois booléens séparés peuvent produire huit combinaisons, dont beaucoup n’ont aucun sens ; trois variantes bien nommées décrivent directement les cas autorisés.

Immutabilité et mise à jour

Un champ lu à travers une valeur ne signifie pas automatiquement que toute la forme peut être modifiée. La variable locale qui contient la forme doit elle-même être mutable pour les affectations acceptées par le langage, et l’analyseur doit autoriser la cible de l’affectation. Garde des mises à jour explicites et utilise des procédures de transformation quand tu veux rendre un changement facile à vérifier.

Construis des noms parlants

Si un type se décrit facilement en une phrase avec ses champs, son nom clarifiera les signatures de toutes les procédures qui l’utilisent.

Commencer par les valeurs que le programme doit représenter

Avant de déclarer un type, écris quelques valeurs concrètes de ton problème. Pour un point, il y a toujours une coordonnée x et une coordonnée y : les deux champs coexistent, donc une form convient. Pour un résultat, l’opération est réussie ou échouée : les cas sont exclusifs, donc un pick convient.

Cette méthode évite deux erreurs fréquentes. Un sac de paramètres indépendants perd leur relation ; une forme contenant un champ pour chaque état possible produit beaucoup de champs inutiles. À l’inverse, une seule forme avec trois booléens autorise des combinaisons qui n’ont peut-être aucun sens. Le type doit refléter les états que le domaine autorise réellement.

Les champs n’imposent pas automatiquement leurs invariants

Une déclaration form Rectangle { minimum: Point, maximum: Point } garantit les deux emplacements et leurs types, mais elle ne dit pas que le point minimum se trouve effectivement avant le point maximum. Cette règle doit être contrôlée par une procédure de validation, une précondition ou une API qui construit la forme de manière contrôlée.

Quand une forme a plusieurs champs dépendants, note son invariant en une phrase. Pour un rectangle : « pour chaque axe, la coordonnée minimum est inférieure ou égale à la coordonnée maximum ». Pour une ligne de panier : « le prix et la quantité sont non négatifs ». Ensuite, identifie tous les endroits qui peuvent construire ou modifier cette forme.

Suivre une variante dans un match

Dans le cas vérifié Resultat::Ok(42), la valeur est construite avec sa variante et sa charge utile. Le bras Resultat::Ok(nombre) récupère le nombre ; le bras Resultat::Echec traite le cas sans donnée associée. Le nom qualifié rappelle à quel type appartient la variante.

Un bras par cas rend le traitement visible, même quand l’outil ne prouve pas l’exhaustivité de toutes les formes avancées. Conserve un retour de repli seulement s’il répond à une décision de conception explicite ; ne l’utilise pas pour cacher un état que tu aurais oublié. Vérifie la règle d’exhaustivité du compilateur ciblé avant de compter dessus.

Mettre à jour un objet sans cacher le changement

Quand un programme change un champ, demande-toi si l’objet entier doit évoluer en place ou si une procédure devrait produire une nouvelle valeur. Dans les cas confirmés par le frontend natif, les tableaux mutables utilisent let mut et set. La mutabilité des champs de forme et le passage par référence dépendent des règles de la construction et du chemin du compilateur ; ne transpose pas une règle d’un type à un autre sans vérification.

Une opération nommée telle que valider_livre ou changer_etat rend souvent une règle métier plus claire qu’une série de modifications dispersées au travers des champs.

Décision corrigée

Un livre avec titre, pagination et auteur est une forme, car ses propriétés coexistent. Son état « disponible, prêté ou en réparation » est un choix, car une seule variante doit être active à la fois. Si l’état « prêté » nécessite une date de retour, place cette donnée dans la charge utile de cette variante plutôt que dans un champ qui resterait valable pour les autres états.

Atelier guidé : dessiner un modèle avant de coder

  1. Sur papier, liste les informations d’un livre : titre, nombre de pages et disponibilité. Crée une form Livre avec des champs typés.
  2. Écris une procédure qui reçoit &Livre et décide si le livre est long. Elle ne doit pas modifier le livre.
  3. Modélise un statut d’emprunt avec pick : disponible, prêté, en réparation. Écris une condition distincte pour chaque variante.
  4. Imagine quelles combinaisons seraient possibles si tu utilisais trois booléens. Compare-les aux variantes du choix nommé.
Corrigé détaillé de l’atelier

Une forme Livre peut regrouper un titre, un nombre de pages et un indicateur d’état si ces propriétés s’appliquent à chaque livre. La procédure qui répond à « est-il long ? » lit les pages et renvoie un booléen ; elle ne doit pas modifier la valeur.

Les états « disponible », « prêté » et « en réparation » sont exclusifs ; un choix nommé évite que trois booléens autorisent simultanément plusieurs états. Si seul un prêt possède une date de retour, place cette donnée avec la variante correspondante quand la représentation est prise en charge, plutôt que de laisser un champ sans sens pour les autres cas.

Une déclaration form ne garantit pas que tous ses champs sont cohérents. Si une date de retour doit être postérieure à la date d’emprunt, écris cette règle et vérifie-la lors de la construction ou de la transition d’état.
