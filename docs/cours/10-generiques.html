Nommer un type existant

Un alias introduit un nom parlant sans inventer une représentation différente. Par exemple :

type IdentifiantClient = u64;

proc charger_client(id: IdentifiantClient) -> bool {
    return id > 0;
}

IdentifiantClient met en évidence la signification de la valeur dans cette API. L’alias reste associé au type qu’il désigne ; il n’apporte pas automatiquement une validation ou une protection contre les conversions accidentelles. Si une nouvelle valeur doit respecter des invariants propres, modélise-la avec une forme ou un type opaque lorsque le compilateur prend en charge ce contrat.

La forme opaque Nom; déclare un type dont la représentation interne n’est pas exposée à ses utilisateurs. Elle permet de protéger une abstraction et de contrôler les opérations qui construisent ou inspectent la valeur. L’usage concret d’un type opaque dépend des fonctions que son module publie.

Une procédure générique

Un paramètre générique est un nom de type valable à l’intérieur d’une déclaration. Une fonction identité peut renvoyer exactement le type qu’elle reçoit :

proc identite<T>(valeur: T) -> T {
    return valeur;
}

T n’est pas un type concret comme i64. C’est une variable de type : au moment de l’utilisation, le compilateur déduit ou vérifie quel type concret remplace T. Les génériques évitent d’écrire séparément la même procédure pour chaque type.

Les déclarations de formes et d’alias peuvent elles aussi avoir des paramètres génériques. Les bibliothèques du dépôt utilisent une notation entre crochets pour des applications de types comme Option[T], et une notation entre chevrons pour déclarer certains paramètres. Consulte la forme des modules locaux : le compilateur peut appliquer des conventions ou prendre en charge des sous-ensembles différents.

Contraindre un paramètre avec une capacité

Une procédure qui compare deux valeurs a besoin que leur type sache les comparer. Un trait sert à nommer ce type de capacité. La grammaire prévoit des déclarations de traits et des déclarations impl qui relient des types à des traits. Une clause where peut exprimer des contraintes de type associées à des génériques.

Un exemple de forme de clause, à lire comme une contrainte, est where T: Comparable. Cela dit que la procédure attend un type T qui satisfait le contrat nommé Comparable. Les traits du module core montrent des signatures de méthodes, comme Display pour écrire une représentation dans un formateur.

trait Affichable {
    proc ecrire(&self, sortie: &mut Tampon) -> bool;
}

Les méthodes de trait peuvent employer &self pour recevoir une référence au récepteur. Ce style appartient au contrat de méthode. Avant d’implémenter un trait pour un type, examine la syntaxe utilisée par la version du compilateur et les modules fournis.

Les limites réelles de l’abstraction

La grammaire peut accepter une construction avant que toutes les étapes du compilateur puissent l’utiliser. La documentation de modules/core précise par exemple que l’intégration de génériques complexes et des implémentations de traits n’est pas encore complète dans le backend natif. Autrement dit, il existe une différence entre une forme reconnue, une forme comprise sémantiquement et une forme qui peut produire un exécutable.

Générique : syntaxe présente, génération refusée

examples/tutorials/generiques-limites.vit sert de cas témoin négatif pour une forme générique.

build/bin/vitte compile examples/tutorials/generiques-limites.vit --emit-c --quiet --no-color --diagnostic=json

Résultat confirmé : code de sortie 1, diagnostic VITTE_BACKEND_E_CODEGEN. La déclaration ne doit donc pas être présentée comme compilable.

Pour apprendre un concept, observe les sources qui le déclarent ; pour planifier un projet, valide-le sur le compilateur effectivement installé. N’annonce pas une capacité à partir de la seule présence d’un fichier de bibliothèque.

Quand une abstraction est utile

Écris d’abord une version simple. Si tu vois plusieurs procédures presque identiques, repère ce qui change et ce qui reste identique. Un générique convient quand la même logique marche réellement avec plusieurs types. Un trait convient quand des types différents partagent une opération avec le même sens. Un alias convient quand un nom de domaine améliore la lecture.

Attention au « générique pour plus tard »

Ajouter plusieurs niveaux de types ou de traits avant d’avoir deux usages concrets rend l’API plus difficile à expliquer. Garde l’abstraction minimale qui supprime la duplication observée.

Atelier guidé : choisir le bon niveau d’abstraction

  1. Écris deux procédures spécialisées qui font le même calcul sur des i64 et des u64. Identifie ce qui est identique et ce qui diffère.
  2. Lis identite<T> et explique pourquoi elle peut renvoyer la même valeur sans connaître toutes les opérations du type T.
  3. Ouvre un trait de modules/core/src/traits/. Reformule en français la promesse de chaque méthode, puis regarde s’il existe une implémentation utilisable dans ce dépôt.
  4. Décide si un nom de domaine devrait être un alias, une forme ou un type opaque. Justifie ton choix par la validation et l’accès aux données attendus.
Auto-évaluation

Un générique est utile si une même logique fonctionne pour plusieurs types. Un trait est utile si ces types promettent le même comportement. Un alias améliore le nom sans créer de représentation distincte ; une forme ou un type opaque sert quand tu dois protéger une valeur et ses invariants.
