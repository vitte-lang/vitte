Décrire les choses qui coexistent avec form

Une forme rassemble les propriétés d’un même objet. Un point possède une coordonnée horizontale et une coordonnée verticale au même moment :

form Point {
    x: i64,
    y: i64,
}

proc somme(point: Point) -> i64 {
    return point.x + point.y;
}

Le nom Point donne un type aux deux nombres et permet de les transmettre ensemble. Les noms des champs rendent leurs rôles visibles ; une signature qui reçoit Point exprime plus clairement son intention que deux paramètres numériques anonymes.

Une forme ne garantit pas à elle seule toutes les règles métier. Un rectangle qui stocke un coin minimum et un coin maximum peut encore avoir un minimum supérieur à son maximum. Il faut décider où cette règle sera vérifiée : à la construction, dans une procédure de validation ou dans un contrat adapté.

Décrire les alternatives avec pick

Un choix nommé représente une valeur qui se trouve dans une variante à la fois. Voici un résultat qui contient soit une valeur, soit un échec :

pick Resultat {
    Ok(i64),
    Echec,
}

proc valeur(resultat: Resultat) -> i64 {
    match resultat {
        Resultat::Ok(nombre) => { return nombre; },
        Resultat::Echec => { return -1; },
    }
    return -2;
}

Dans le bras Ok, nombre reçoit la charge utile. Dans le bras Echec, aucune valeur n’est disponible. Ce modèle distingue un résultat absent d’une valeur numérique ordinaire. Le code -1 de cette fonction n’est qu’une convention de l’exemple ; dans une API, renvoyer un autre pick peut préserver la distinction entre résultat et échec.

La différence de représentation change le raisonnement

Suppose qu’un téléchargement puisse être en attente, terminé ou échoué. Trois booléens peuvent représenter huit combinaisons ; plusieurs ne veulent rien dire, comme « terminé et en attente ». Un pick Etat { EnAttente, Termine, Echec } nomme seulement les cas utiles.

Si une variante doit transporter une information, donne-lui une charge utile adaptée : un échec peut contenir un code ou une position. Garde chaque donnée près de la variante à laquelle elle appartient. Cette structure évite qu’un champ d’erreur reste renseigné alors que l’opération a réussi.

Dans l’autre sens, ne transforme pas en variantes des propriétés qui peuvent coexister. Un utilisateur qui a un identifiant, un nom et une adresse est une forme, même si chacune de ces valeurs peut être modifiée séparément.

Lire puis décomposer l’exemple vérifié

Le fichier formes-choix.vit combine les deux idées : il construit un Point, puis construit Resultat::Ok(42) et récupère la charge utile avec match. Le fichier complet s’exécute avec le frontend natif :

build/bin/vitte run examples/tutorials/formes-choix.vit --quiet --no-color

Résultat confirmé : code de sortie 0. Pour apprendre chaque étape séparément, commente la procédure valeur, vérifie la lecture des champs de Point, puis rétablis la procédure et suis les deux bras de match.

Une méthode de conception en quatre questions

  1. Quelles propriétés existent simultanément ? Regroupe-les dans une forme.
  2. Quels cas s’excluent mutuellement ? Énumère-les dans un choix.
  3. Quelle information est nécessaire dans chaque cas ? Place-la dans la charge utile de la variante concernée.
  4. Quelle règle doit toujours rester vraie ? Écris-la en une phrase et décide où la contrôler.

Quand tu hésites, écris deux ou trois valeurs concrètes que le type devrait pouvoir représenter. Puis cherche une combinaison qui serait invalide. Si elle peut être construite facilement, le modèle peut probablement être amélioré.

Modéliser une transition, pas seulement un état

Un choix décrit les états possibles ; les procédures décrivent les transitions permises entre eux. Pour une réservation, on peut définir une opération confirmer qui accepte l’état disponible et refuse un état déjà annulé. Le type seul ne précise pas quelles transitions sont permises : il faut les écrire dans la logique de l’application et les vérifier avec des exemples.

Avant d’ajouter une procédure de transition, construis une table :

État courantOpérationRésultat attendu
DisponibleconfirmerConfirmée
ConfirméeannulerAnnulée
AnnuléeconfirmerRefus ou résultat d’erreur

Cette table évite de coder une branche qui n’a jamais été décidée. Si une transition invalide peut arriver normalement, représente son refus dans la sortie de la procédure. Si elle révèle une erreur de programmation, un contrat peut être plus adapté.

Placer une donnée dans la variante qui la justifie

Supposons que seule une annulation ait une raison. Si la raison est un champ de la forme, elle doit recevoir une valeur même quand la réservation est disponible ou confirmée. Un pick peut au contraire placer cette donnée dans la variante qui en a besoin. Les types avec charge utile existent dans le dépôt, comme Resultat::Ok(i64).

Évite de dupliquer la même information dans un champ et dans une variante. Deux sources de vérité peuvent diverger après une modification. Choisis l’endroit qui est naturellement propriétaire de la règle et adapte les procédures d’accès à ce modèle.

Vérifier la construction réelle d’un modèle

Le fichier formes-choix.vit fournit une preuve de construction d’une forme, de lecture de ses champs, de construction d’un pick avec charge utile et de récupération de cette charge dans match. Cette preuve est plus forte qu’une déclaration isolée dans la grammaire, mais elle reste limitée aux types et opérations exercés par ce programme.

Pour une forme imbriquée, un champ mutable, une référence vers une variante ou une correspondance plus complexe, écris un petit fichier distinct. Ne déduis pas qu’une propriété avancée fonctionne parce qu’un exemple voisin fonctionne.

Une règle de modèle à vérifier

Si une réservation est confirmée, elle doit posséder son numéro de confirmation. Un modèle qui garde un numéro facultatif dans toutes les variantes nécessite une règle de validation. Un modèle qui place ce numéro uniquement dans la variante « confirmée » rend la relation plus explicite, sous réserve de vérifier que cette forme est prise en charge par la cible utilisée.

Atelier avancé : état d’une réservation

  1. Une réservation possède un numéro et une date : décris ces propriétés avec une forme.
  2. Une réservation est disponible, confirmée ou annulée : décris les états exclusifs avec un choix.
  3. Ajoute une charge utile à l’annulation pour conserver la raison. Écris les bras d’un match qui traitent les trois variantes.
  4. Énumère une règle métier, par exemple « une réservation confirmée possède un numéro de confirmation ». Décide si cette règle appartient au modèle, à une validation ou à un contrat.
Correction détaillée

Le numéro et la date coexistent : ils appartiennent donc à une form Reservation. Les états « disponible », « confirmée » et « annulée » s’excluent : ils forment un pick EtatReservation. La raison ne concerne que l’annulation ; place-la avec cette variante si la syntaxe exacte est acceptée par la cible utilisée.

Les transitions autorisées peuvent être disponibles → confirmée, confirmée → annulée, et indisponible → refus. La dernière situation peut être un résultat d’erreur normal ou une précondition violée selon la provenance de l’appel.

La preuve du dépôt confirme un pick avec charge utile et un match dans une fixture précise. Elle ne confirme pas automatiquement chaque façon d’imbriquer des types ou des charges utiles.
