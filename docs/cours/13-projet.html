Le comportement à construire

Notre panier contient des lignes. Chaque ligne a un prix unitaire et une quantité. Le total correspond à la somme des sous-totaux. On va construire un calculateur qui donne un total et refuse les valeurs incohérentes. Cette version reste volontairement petite : aucun fichier, réseau ou affichage n’est nécessaire pour comprendre la logique.

Étape 1 : modéliser une ligne

Une ligne possède deux données à la fois. Une form est donc plus claire que deux nombres isolés transmis à toutes les procédures :

space cours::panier;

form Ligne {
    prix_unitaire: i64,
    quantite: i64,
}

proc sous_total(ligne: &Ligne) -> i64 {
    return ligne.prix_unitaire * ligne.quantite;
}

Le nom Ligne représente une idée du domaine. La procédure sous_total reçoit une référence car elle a besoin de lire les champs sans transformer la ligne. La multiplication est au même endroit pour tous les appels ; si la règle change, on sait où la modifier.

Étape 2 : décrire la règle métier

Une quantité négative n’a pas de sens pour ce panier. Une première version peut retourner un code simple, mais un code numérique anonyme n’explique pas la nature de l’échec. À mesure que le programme grandit, représente les cas de réussite et d’erreur par un type nommé ou un pick.

pick ErreurPanier {
    Aucune,
    QuantiteNegative,
    PrixNegatif,
}

proc ligne_valide(ligne: &Ligne) -> bool {
    return ligne.prix_unitaire >= 0 and
           ligne.quantite >= 0;
}

On pourrait aussi imposer les conditions avec des clauses requires. Un contrat est approprié si un appel invalide indique une faute de programmation. Un résultat d’erreur explicite est plus adapté si l’entrée vient d’un utilisateur et que le programme doit continuer après l’avoir refusée.

Étape 3 : parcourir plusieurs lignes

Un panier simple peut être un tableau de taille fixe. Ce choix convient lorsque la capacité est connue, comme dans un petit exercice. Dans un programme réel où le nombre de lignes varie, choisis une collection dont les règles d’allocation sont effectivement disponibles dans la bibliothèque et le backend que tu utilises.

proc total_panier(lignes: &[3]Ligne) -> i64 {
    let mut total: i64 = 0;
    for index in 0..3 {
        set total = total + sous_total(&lignes[index]);
    }
    return total;
}

On parcourt les indices de zéro à trois, sans inclure trois dans la plage. C’est cohérent avec les trois positions 0, 1 et 2. Si la taille change, le code ne devrait pas garder un 3 caché dans plusieurs endroits : introduis une constante ou une abstraction de collection adaptée.

Le projet complet est un modèle pédagogique, pas encore une commande confirmée

Le parcours utilise une boucle for sur plage et des déclarations test. Ces constructions n’ont pas de preuve d’exécution complète dans le backend audité. Pour lancer des versions confirmées des briques, essaie formes-choix.vit, tableaux.vit et contrats.vit.

Étape 4 : couvrir les cas par des tests

test "ligne avec prix nul et quantité nulle" {
    let ligne: Ligne = Ligne {
        prix_unitaire: 0,
        quantite: 0,
    };
    assert(sous_total(&ligne) == 0);
}

test "sous-total de deux articles" {
    let ligne: Ligne = Ligne {
        prix_unitaire: 6,
        quantite: 2,
    };
    assert(sous_total(&ligne) == 12);
}

Ces tests donnent un cas de frontière et un cas ordinaire. Ajoute ensuite un cas de plusieurs lignes, une quantité nulle et chaque erreur prévue. Les tests nommés servent aussi de documentation exécutable : quelqu’un qui découvre le module comprend les règles en parcourant les noms et les assertions.

Étape 5 : organiser le projet

Quand le fichier devient trop long, place le modèle dans un module, les règles de calcul dans un autre et le point d’entrée dans un troisième. Exporte seulement les types et procédures dont les autres modules ont besoin. Garde les tests près du comportement qu’ils protègent et note la version d’outil utilisée.

Travaille par petites étapes : un modèle, une procédure, un test, puis le changement suivant. Après chaque étape, lance la commande de vérification disponible. Si tu bloques, réduis l’exemple au plus petit fichier qui reproduit le diagnostic et compare-le à une construction existante dans le dépôt.

Continuer après le cours

Choisis un petit projet qui t’intéresse : un convertisseur d’unités, un analyseur de texte, un carnet de scores ou un outil en ligne de commande. Écris d’abord deux phrases sur ses comportements ; transforme chaque phrase en procédure et en tests ; puis ajoute les fichiers et les modules nécessaires.

Pour explorer une notion, pars de la grammaire et des tests du dépôt pour trouver des cas concrets. Consulte aussi les bibliothèques core et la page État du support, qui aide à distinguer ce qui est spécifié de ce qui fonctionne dans le compilateur. Tu sais maintenant lire les éléments essentiels du langage et poser les bonnes questions avant de dépendre d’une fonctionnalité.

Tu peux reprendre le cours quand tu veux

Si une leçon reste floue, réécris son exemple de mémoire, puis compare avec le cours. Expliquer une idée avec tes propres mots est souvent le meilleur test de compréhension.

Atelier final : faire une petite livraison

  1. Écris une courte description du besoin : quelles données entrent, quel résultat doit sortir, et quelles entrées doivent être refusées ?
  2. Implémente Ligne, sous_total et la validation. Vérifie chaque changement avant d’ajouter le suivant.
  3. Ajoute des tests pour les cas normal, zéro et invalide. Si ton compilateur ne prend pas en charge une construction montrée dans le cours, remplace-la par une forme déjà utilisée par le dépôt et note cette décision.
  4. Déplace modèle, calculs et point d’entrée dans des modules distincts. Réduis les exports au minimum utile.
  5. Relis ton code comme une autre personne : peut-elle prédire le résultat, comprendre le traitement des erreurs et repérer les limites du programme ?
Comment savoir si ton projet est terminé ?

Tu peux expliquer le modèle, lancer les vérifications disponibles, montrer les cas couverts par les tests et énumérer les limites connues. Un projet terminé n’est pas forcément grand : ses comportements et ses frontières sont clairs.
