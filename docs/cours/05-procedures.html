Elle reçoit des paramètres, calcule quelque chose et peut renvoyer un résultat que d’autres procédures réutilisent. takeaway: Une bonne procédure a une responsabilité lisible, des entrées explicites et un résultat dont le type est annoncé. practice: "Découpe un calcul de prix en trois procédures : calculer le sous-total, appliquer la remise et produire le prix final." ---

La forme générale d’une procédure

proc additionner(gauche: i64, droite: i64) -> i64 {
    return gauche + droite;
}

proc introduit la déclaration. additionner est le nom de la procédure. Les noms dans les parenthèses sont des paramètres : ce sont les entrées que l’appelant fournit. Chaque paramètre a un type explicite. Après la flèche, i64 annonce le type de retour. Le corps entre accolades effectue le travail et return renvoie la valeur calculée.

On peut ensuite appeler cette procédure depuis une autre procédure :

proc total_du_panier() -> i64 {
    let sous_total: i64 = additionner(18, 24);
    return sous_total;
}

Les arguments 18 et 24 occupent les places des paramètres gauche et droite. Le nombre, l’ordre et le type des arguments doivent correspondre à la déclaration.

Exemple vérifié : paramètres, appels et retour

examples/tutorials/procedures.vit compose un sous-total puis ajoute la livraison ; le calcul attendu vaut 42.

build/bin/vitte run examples/tutorials/procedures.vit --quiet --no-color

Résultat confirmé : code de sortie 0.

Décomposer plutôt que tout entasser

Une procédure devrait répondre à une question précise. Si une fonction de 80 lignes valide une entrée, calcule plusieurs valeurs, transforme un résultat et affiche un rapport, sépare ces responsabilités. Des procédures courtes rendent les tests plus ciblés et les noms racontent le déroulement.

Les paramètres rendent les dépendances visibles. Une procédure qui a besoin d’un taux de remise devrait généralement le recevoir en paramètre plutôt que de dépendre d’une variable globale cachée. Le code d’appel devient alors une petite description de ce qui est calculé.

Retourner une valeur ou terminer sans valeur

Quand le type de retour est renseigné, chaque chemin normal doit produire une valeur compatible. Certaines procédures servent plutôt à effectuer une action, comme écrire un message. Selon les primitives et les conventions du module, elles peuvent avoir un type de retour sans valeur, souvent nommé void. Le point d’entrée d’exemple renvoie un entier comme statut de fin.

Évite de mélanger plusieurs styles dans une même abstraction. Si une procédure calcule un prix, renvoie le prix ; si elle imprime un rapport, choisis un nom d’action et laisse son effet visible dans le nom ou la documentation.

Références en paramètre

Pour examiner une valeur composée sans la copier dans chaque appel, la grammaire permet un paramètre de référence comme point: &Point. Le corps peut lire ses champs via point.x. C’est une manière de montrer que la procédure consulte une donnée existante. Les règles détaillées de mutabilité, d’alias et de durée de vie dépendent de l’implémentation disponible ; ne suppose pas un système d’emprunt plus riche que ce que le compilateur vérifie.

form Point {
    x: i64,
    y: i64,
}

proc somme(point: &Point) -> i64 {
    return point.x + point.y;
}

Contrats : écrire les préconditions et postconditions

La grammaire de Vitte permet de placer des clauses requires et ensures avant le corps d’une procédure. Une précondition décrit ce que l’appelant doit garantir. Une postcondition décrit ce que la procédure promet après son retour. Dans une postcondition, le nom result désigne la valeur produite.

proc ajouter_un(valeur: i64) -> i64
    requires valeur < 100;
    ensures result == valeur + 1;
{
    return valeur + 1;
}

Le contrat clarifie l’usage prévu et donne au compilateur des propriétés à analyser. Ici, la précondition empêche un dépassement vers la borne supérieure lors de l’ajout ; la postcondition décrit exactement le résultat promis. Une spécification doit refléter les limites du type et de l’opération. Les contrats peuvent produire des diagnostics ou des vérifications à l’exécution selon ce que le compilateur arrive à prouver.

Récursion et arrêt

Une procédure peut s’appeler elle-même. C’est la récursion. Une version récursive d’un calcul doit avoir un cas de base et un appel qui se rapproche de ce cas ; sans cela, elle ne termine pas. Pour un parcours prévisible et simple, une boucle est parfois plus facile à suivre. Choisis la forme qui rend la condition d’arrêt la plus évidente.

Avant de créer une procédure

Dis en une phrase ce qu’elle reçoit, ce qu’elle renvoie et ce qu’elle ne fait pas. Si la phrase contient plusieurs tâches indépendantes, cherche un découpage.

Concevoir une signature avant le corps

La signature est le premier contrat lisible d’une procédure. Écris-la avant les instructions et vérifie chacun de ses éléments :

  • Le nom répond-il à une question précise, comme sous_total ou valider_ligne ?
  • Les paramètres nomment-ils les entrées et indiquent-ils leur type ?
  • Le type de retour dit-il exactement quelle information le corps produit ?
  • La procédure a-t-elle besoin de données qu’elle ne reçoit pas explicitement ?

Deux paramètres du même type peuvent être intervertis sans que le compilateur puisse comprendre l’intention métier. Des noms tels que prix et quantite aident donc autant le lecteur que le diagnostic. Si l’ordre est trop facile à inverser, une forme avec des champs nommés peut rendre l’appel plus explicite.

Suivre un appel et son retour

Dans l’exemple vérifié du panier, main appelle d’abord sous_total(6, 6). La procédure renvoie 36. La procédure appelante transmet ensuite cette valeur à avec_livraison(36, 6, 6), qui renvoie 42. La valeur ne saute pas directement de la première ligne au résultat : chaque appel possède ses paramètres, son corps et son retour.

Cette lecture fournit une méthode de débogage. Note les arguments à l’entrée de la procédure, calcule les expressions locales dans l’ordre, puis note la valeur au return. Si le résultat final est faux, compare la première étape où ta trace diverge du résultat observé.

Valeur de retour et chemins de contrôle

Pour une procédure déclarée -> i64, chaque chemin normal doit pouvoir produire un i64. Dans une condition, vérifie toutes les branches : une branche qui ne renvoie rien peut rendre le corps incomplet. Le retour anticipé est utile quand il clarifie un cas particulier, mais trop de sorties dispersées rendent la lecture du résultat plus difficile.

Une procédure d’action n’a pas le même objectif qu’une procédure de calcul. Une procédure appelée afficher_resume annonce un effet ; une procédure appelée calculer_total annonce une valeur. Garder les noms et les types cohérents aide l’appelant à savoir s’il doit utiliser un résultat ou simplement appeler l’action.

Récursion : prouver le rapprochement du cas simple

Une procédure récursive se rappelle sur un problème plus petit. Pour calculer une somme jusqu’à n, l’idée mathématique est : la somme de 1 à 1 vaut 1 ; pour une valeur supérieure, la somme jusqu’à n est n plus la somme jusqu’à n - 1. Le cas simple empêche les appels de continuer sans fin, et chaque appel doit s’en rapprocher.

Avant d’écrire une récursion, réponds à trois questions : quel est le cas d’arrêt ? Quelle mesure diminue ? Quel résultat chaque appel promet-il ? Vérifie également la profondeur maximale et le risque de dépassement numérique. Ces questions portent sur l’algorithme ; elles ne garantissent pas que chaque version du backend supporte le cas précis.

Pour un calcul répétitif simple, une boucle while est souvent plus facile à tracer avec les constructions runtime confirmées. La récursion reste utile lorsque le problème est naturellement défini par des sous-problèmes, mais vérifie la compilation avant d’en faire le fondement d’un programme.

Correction de l’appel en chaîne

additionner(18, 24) renvoie 42 ; total_du_panier lie cette valeur à sous_total, puis la renvoie. Le nom local ne crée pas une nouvelle opération : il donne un repère à la valeur calculée par l’appel.

Atelier guidé : transformer une recette en procédures

  1. Écris sous_total(prix, quantite). Donne un nom et un type à chaque paramètre et retourne le produit.
  2. Écris ajouter_livraison(sous_total, livraison) au lieu de recopier l’addition dans plusieurs endroits.
  3. Écris prix_final qui appelle les deux procédures précédentes. Vérifie que les paramètres racontent les données transmises.
  4. Ajoute un contrat à la procédure de livraison. Note une hypothèse que l’appelant doit garantir et une propriété attendue de la valeur renvoyée.
Corrigé détaillé de l’atelier

sous_total(prix, quantite) reçoit ses deux données et renvoie leur produit. Pour le cas 6 et 2, elle donne 12. ajouter_livraison(sous_total, livraison) reçoit ce résultat et le coût de livraison ; avec une livraison de 5, elle renvoie 17. prix_final compose les deux appels, sans recopier leurs formules.

Un contrat possible exige que le sous-total et la livraison soient non négatifs. Une postcondition pourrait préciser que le résultat est la somme de ces deux entrées. Il faut traiter les limites numériques : la non-négativité seule ne garantit pas qu’une addition ne dépasse jamais la plage du type.

La correction est bonne si chaque procédure peut être expliquée par une phrase et si ses entrées sont visibles dans la signature. Les exemples de contrats du dépôt passent par le chemin de compatibilité ; vérifie ce chemin avant de conclure que le même contrat s’exécute dans chaque frontend.
